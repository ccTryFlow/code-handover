# CodeHandover 现场讲解与操作文档

这份文档用于发布前或直播讲解时边操作边说明。建议准备一个真实但不敏感的 Git 仓库作为演示项目，优先选择提交历史清晰、作者较少、目录结构有代表性的项目。

## 1. 讲解目标

让听众在 15 到 25 分钟内理解三件事：

- CodeHandover 是一个桌面端代码交接文档生成工具，不是普通网页应用。
- 它会结合 Git 作者、提交时间、项目结构、语言框架、AST 符号和关键文件，生成个人维度的交接文档。
- 开源发布只提供 Windows x64 `.exe` 和 `.msi` 安装包，源码仓库保持公开、可提 issue、可二次修改。

推荐开场话术：

> CodeHandover 解决的是代码交接里最麻烦的一件事：不是简单列文件，而是把某个交接人真实参与过的代码、接口、命令、配置、风险和后续补充点整理成一份可以继续编辑的文档。

## 2. 演示前准备

| 检查项 | 操作 | 通过标准 |
| --- | --- | --- |
| 安装包 | 从 GitHub Release 下载 Windows x64 `.exe` 或 `.msi` | 能正常安装和打开 |
| 演示仓库 | 准备本地 Git 项目 | `git log` 能看到作者和提交历史 |
| 敏感信息 | 检查演示仓库 | 不展示生产密钥、客户数据、私有 Token |
| AI 配置 | 可选 | 未配置也可以演示主流程 |
| 输出目录 | 确认项目目录可写 | 能生成 `handover_项目名.md/html/pdf` |

本机发布前检查命令：

```bash
npm run check
npm run security:audit
```

如果需要验证安装包发布配置：

```bash
npm run release:guard
```

## 3. 推荐演示路线

### 3.1 首页：说明产品定位

操作：

1. 打开 CodeHandover。
2. 停留在首页。
3. 指向“选择本地项目”和“拉取远程仓库”两个入口。

讲解重点：

- 这是 Electron 桌面应用，因为它需要访问本地 Git、读取本地目录、生成本地文档。
- 普通线上网站不适合直接做这个工具，因为浏览器无法安全、完整地读取用户本地 Git 仓库。
- 远程仓库 Token 只用于本次 clone，不会写回克隆后的 `origin` 地址。

可讲话术：

> 这个软件不是让大家把代码上传到一个网站分析，而是尽量把分析过程留在本机。它适合处理公司内部项目，因为交接文档和源码都比较敏感。

### 3.2 选择本地项目

操作：

1. 点击“选择本地项目”。
2. 点击“选择目录”。
3. 选择演示 Git 仓库根目录。
4. 确认 Git 状态显示已识别仓库和当前分支。
5. 点击“下一步”。

讲解重点：

- 软件会检测当前目录是否是 Git 仓库。
- 如果是 Git 仓库，会读取当前分支和作者提交历史。
- 非 Git 仓库也能做基础结构分析，但不能按作者生成个人贡献范围。

现场提醒：

- 如果选错目录，返回重新选择。
- 如果仓库很大，第一次分析会稍慢，建议提前准备中等规模项目。

### 3.3 分析配置：选择交接人和范围

操作：

1. 确认“启用 Git 作者分析”为开启。
2. 在“选择交接人”里选择一个提交较多的作者。
3. 时间范围先选“全部时间”，第二轮可演示“自定义”。
4. 输出格式建议先选 Markdown。
5. AI 摘要保持关闭，除非现场已经配置好模型。

讲解重点：

- 作者选择优先按 email 匹配，减少同名作者造成的归属错误。
- 时间范围决定本次交接文档覆盖的提交边界。
- Markdown 适合二次编辑，HTML 适合浏览器阅读，PDF 适合归档。
- AI 摘要只是增强项，核心分析不依赖 AI。

可讲话术：

> 这里最重要的是“交接人范围”。文档不会把全项目都算到某个人头上，而是优先根据 Git 作者和时间范围收敛到这个人实际参与过的代码。

### 3.4 分析进度：解释软件在做什么

操作：

1. 点击“开始分析”。
2. 停留在进度页，观察阶段和日志。
3. 等待分析完成后点击“查看结果”。

讲解重点：

- 扫描项目结构和关键文件。
- 识别语言、框架和启动命令。
- 读取 Git 提交、作者、改动文件和增删行。
- 扫描关键代码文件并生成结构化分析。
- 导出交接文档。

可讲话术：

> 进度页不是简单的加载动画，它会把每个阶段的分析动作展示出来。这样现场如果项目太大或者 Git 历史异常，也能看到卡在哪一步。

### 3.5 结果页：讲清分析价值

操作：

1. 查看顶部项目名称、分支、文档状态。
2. 说明主要语言、扫描文件、模块、Git 作者、AST 符号等指标。
3. 展示技术栈识别。
4. 展示 Tree-sitter AST 结构分析。
5. 展示 Git 作者贡献表。
6. 点击“打开文档”或“重新生成文档”。

讲解重点：

- 技术栈识别不是只看文件后缀，还会结合依赖清单、目录结构和关键文件。
- AST 用来抽取类、函数、方法、调用、导入等结构信息。
- Git 作者贡献用于确定个人责任边界。
- 最终文档是交接起点，不是替代负责人补充业务细节。

可讲话术：

> 我最关心的不是“这个项目用了什么语言”这么简单，而是它能把一个人的贡献范围、关键文件、可能风险和需要补充的交接点整理出来。

### 3.6 打开交接文档：重点讲文档结构

操作：

1. 打开生成的 Markdown、HTML 或 PDF。
2. 依次展示文档目录。
3. 重点停留在“个人涉及接口、命令、数据和配置”“关键代码逻辑和方法备注”“交接重点和风险”。

讲解重点：

- 文档只展开所选作者涉及过的文件。
- 接口、命令、数据表和配置来自个人责任范围内的文件，不应把全项目误算进来。
- 方法备注会说明分支、循环、事务、数据访问、外部调用、权限、文件处理等逻辑线索。
- 文档中仍建议负责人补充真实业务规则、异常场景和测试入口。

可讲话术：

> 交接文档最怕两种情况：一种是太空，只写“有导入功能”；另一种是太泛，把全项目都塞给一个人。这个工具的目标是把范围收准，再把逻辑线索讲清楚。

## 4. GitHub 开源讲解

操作：

1. 打开 GitHub 仓库主页。
2. 展示 README、LICENSE、Issues、Releases。
3. 打开 Releases，说明只保留 Windows x64 `.exe` 和 `.msi`。

讲解重点：

- 仓库是 public，别人可以 clone、fork、提 issue。
- 使用 MIT License，允许二次修改和分发，但需要保留许可证声明。
- Issues 已开放，用户可以反馈 bug 和功能建议。
- Release 不上传 `win-unpacked`、`.blockmap`、`latest.yml`、`ia32` 或 portable 包。

可讲话术：

> 开源不是只把代码推上去。仓库要公开、协议要清楚、安装包要干净、问题反馈入口要留好，这样别人才能真正使用和参与。

## 5. 现场兜底方案

| 问题 | 现场处理 |
| --- | --- |
| 作者下拉为空 | 确认选择的是 Git 仓库根目录，并且仓库有提交历史 |
| 分析时间过长 | 换成提前准备的小仓库，或选择最近 3 个月 |
| AI 不可用 | 关闭 AI 摘要，主流程不依赖 AI |
| 文档打不开 | 到项目目录里手动打开 `handover_*.md/html/pdf` |
| PDF 生成失败 | 改用 Markdown 或 HTML 演示 |
| 本地打包失败 | 使用 GitHub Actions 生成的安装包，Windows 本地打包可能需要开发者模式或管理员权限 |

## 6. 发布前质量检查清单

发布或讲解前建议逐项确认：

- `npm run check` 已通过。
- `npm run security:audit` 已通过。
- GitHub Actions 最近一次 main 分支 CI 已通过。
- GitHub 仓库为 public。
- GitHub Release 只保留 Windows x64 `.exe` 和 `.msi`。
- `.env`、Token、私有仓库地址、生成的交接文档没有提交。
- 打开软件不会自动弹出 DevTools。
- 浏览器直接访问构建产物时不会当成完整应用使用。
- 真实仓库演示能完成：选择项目、选择作者、开始分析、查看结果、打开文档。

## 7. 一句话总结

> CodeHandover 的核心价值，是把 Git 责任边界、代码结构和交接风险整理成一份可继续编辑、可归档、可追问的个人交接文档。
